TL;DR
======================================================================

  on a web page.
- It lives in your private GitHub repo:
  https://github.com/spacekut/accessibility-qa-skill

  certificate.


======================================================================
1. WHAT IT IS
======================================================================
A skill is a markdown file (SKILL.md) that tells Claude Code how to do a
particular job. This one tells Claude how to run a beginner-friendly
accessibility baseline:

  - what can be AUTOMATED (axe-core scan, names/roles, contrast numbers)
  - what must be checked BY HAND (keyboard, screen reader, zoom, colour cues)
  - how to RECORD the results honestly (Pass / Issue / Not verified / Not run)

It follows WCAG 2.2 AA, using the W3C page as the reference:
https://www.w3.org/WAI/standards-guidelines/wcag/

3. HOW SOMEONE USES IT
======================================================================
WITH Claude Code
  1. Copy the folder .claude/skills/accessibility-qa/ into a project's
     .claude/skills/  (or into ~/.claude/skills/ to use it everywhere).
  2. Start a NEW Claude Code session.
  3. Ask in plain language, for example:
       "Run an accessibility baseline on https://example.com/checkout"
       "Do a keyboard test on this page"
  4. Live browser checks need a Playwright MCP server. Without one, the
     skill gives commands and marks them "Not run".

WITHOUT Claude Code
  The file does nothing by itself, but the method works as a checklist:
    Automated scan  -> axe DevTools extension or the axe command-line tool
    Keyboard pass   -> Tab, Shift+Tab, Enter, Space, Escape, arrow keys
    Screen reader   -> a person with VoiceOver (Cmd+F5 on a Mac)
    Contrast        -> browser DevTools or any contrast checker
    Report          -> copy the table from the example report
  (We did not try the axe extension or command-line tool ourselves.)


======================================================================
4. HOW THE SKILL WORKS (THE 8 STEPS)
======================================================================
  1. Scope       page, one task, states, browser, desktop/mobile
  2. Standards   WCAG 2.2 AA; look criteria up before citing them
  3. Automated   run axe etc. only if tools exist; never pretend
  4. Keyboard    one real task, Tab order, focus, Enter/Escape, no trap
  5. Screen reader   spot-check the same journey (needs a person)
  6. Contrast / visual   colour not the only cue, zoom, reflow
  7. Record      table + findings with evidence
  8. Next steps  a few high-impact ones, not a giant list

THE REPORT TABLE (required, exactly three columns)
  | Test Scenarios | Test Steps | Test Result |

Every Test Result starts with ONE of these:
  Pass              the check was run and met expectations
  Issue (F#)        reproduced or measured in the page; F# = finding number
  Not verified (F#) suspected from code or a scan, not reproduced
  Not run           not executed (for example no screen reader)

KEY RULES (guardrails)
  - Never claim a test was run unless it was.
  - A clean axe result does NOT mean the page is accessible.
  - Do not claim full WCAG conformance from a limited check.
  - Prefer plain HTML and native controls over extra ARIA.
  - Do not call a mismatch a defect until intended behaviour is confirmed.
  - Clean up browser artifacts afterwards (screenshots, snapshots, logs).

5. THE WORKED EXAMPLE (BLIND TEXT GENERATOR)
======================================================================
Page: https://www.blindtextgenerator.com/lorem-ipsum  (public)
Run : Chromium via Playwright, desktop, plus a 320px reflow check.

CONFIRMED
  F1  The words-count field has no label (axe: critical).
  F2  The page does not reflow at 320px (width 960, no viewport meta tag).
  F3  The second tab stop (the "Russian" language link) is off-screen and
      shows no visible focus.

SUSPECTED, NEEDS A MANUAL RETEST (read from the page code)
  F4  The copy-to-clipboard control is an image with a click handler, not
      reachable by keyboard.
  F5  No landmarks, no skip link, five visible h1 headings.
  F6  The "Text copied" message has no live region.
  F7  Many small touch targets (axe said 20; not confirmed).

NOT DONE
  - Screen reader pass.
  - Contrast (axe left 21 text elements undecided).
  - Generating other texts, other pages, real mobile devices.

6. TESTING THE SKILL ITSELF (DEMOS)
======================================================================
We started a separate Claude Code session in a throwaway project, installed
the skill there, and gave it a prompt like a new user would.

DEMO 1 (before the table was tightened)
  - The skill was invoked (confirmed in the session transcript).
  - It matched our findings on the label, the reflow and the missing skip
    link, and it was careful about what it had not verified.
  - It called the logo link "unnamed", which our run showed is wrong (the
    image has alt text). It said it had not checked the alt text.
  - It reported 9 small targets; we got 20. It used a newer axe version
    (4.14.0 vs 4.10.2). We did not investigate the difference.
  - It did NOT use the exact required table.

DEMO 2 (after the table was tightened, repo commit 42d85f7)
  - The skill was invoked (confirmed in the session transcript).
  - It used the required three-column table, and its results used the
    required values (Pass / Issue / Not verified / Not run, with F# links).
    So the tightening worked.
  - It stayed honest: it listed what it did not run (screen reader,
    contrast, zoom, the actual copy step), said it had not looked up W3C
    criteria so it cited no numbers, and wrote no files as asked.
  - Weaker points:
      * It reported "a skip link exists, just not in the first 4 stops".
        We checked: that link is a "[î] Top" back-to-top link at the
        bottom of the page, NOT a skip link. The repo's example report
        ("no skip link found") is still correct. The demo hedged it as
        "not verified", but the claim was still wrong.
      * It again called the first link "unnamed" (our run showed it is
        named by the logo's alt text), and again said "9 small targets"
        (we got 20; newer axe version).
      * It did not find the off-screen "Russian" link we found (F3). It
        only said focus visibility was "not verified".
      * One row has a slightly odd result ("Not verified (F2)" for the
        scan while F1 was confirmed). Allowed by the rules, but untidy.
  - Takeaway: the format now holds up. Accuracy of individual findings
    still depends on how deep each run goes, which is why the skill labels
    anything not reproduced as "Not verified".

8. COMPANION SKILL: API TESTS FROM A TICKET (QUICK START)
======================================================================
Repo: spacekut/api-tests-from-ticket-skill  (PRIVATE)
A generic skill, written from scratch. It turns a ticket's requirements
into API regression tests. Trialled once on a made-up ticket against a
public fake API. Not yet tried on a real ticket.

Before a first real run, go through PREP-CHECKLIST.md in that repo. It
covers permission, the ticket, where endpoints come from, the test
environment, credentials, what to check afterwards, and red flags.

QUICK START
  1. Install: copy .claude/skills/api-tests-from-ticket/ into a project's
     .claude/skills/ (or ~/.claude/skills/). Start a new Claude Code
     session.
  2. Have the ticket text and a TEST environment URL ready. Never use
     production.
  3. Set credentials as environment variables (for example API_BASE_URL).
     Do not paste secrets into the chat.
  4. Ask: "Write API tests for TICKET-123".
  5. Review the traceability table BEFORE it generates anything. This is
     where you fix wrong assumptions.
  6. Run the tests. The skill tells you the command. For Node it looks
     like:
       API_BASE_URL=https://your-test-env node --test path/to/tests.mjs
  7. Read the results:
       Pass          it ran and the assertion held
       Fail          it ran and did not match. Could be a product bug, a
                     wrong expectation in the ticket, or a test/data
                     problem. The skill will not weaken an assertion to
                     turn it green.
       Blocked / Not run   something stopped it (for example missing
                     credentials)
  8. Keep the tests by committing them to your project's test folder.
     The skill does not commit or push unless you ask.

TRIAL RESULT (2026-11-05)
  - 7 tests generated, 5 passed, 2 failed.
  - Both failures were ticket-versus-environment mismatches (the fake API
    has no auth, and DELETE returned 200 where a comment asked for 204).
    They were reported as failures and the assertions were not weakened.
  - Not exercised: the pause to review the table (the run was
    non-interactive), cleanup of created data, real authentication, and a
    real ticket tracker.

9. COMPANION SKILL: BUG TO TEST SCENARIOS (QUICK START)
======================================================================
Repo: spacekut/bug-to-test-scenarios-skill  (PRIVATE)
A generic skill, written from scratch. It turns one bug report into a
small set of test scenarios: reproduce the bug, verify the fix, variants
of the same cause, neighbouring behaviour, and "does not break" checks.
Trialled once on a made-up bug. Not yet tried on a real bug.

QUICK START
  1. Install: copy .claude/skills/bug-to-test-scenarios/ into a project's
     .claude/skills/ (or ~/.claude/skills/). Start a new Claude Code
     session.
  2. Have the bug ready: description, steps to reproduce, expected and
     actual behaviour, environment, and EVERY comment. Add the fix or
     pull request and any spec if you have them.
  3. If the bug belongs to an employer or client, check you are allowed to
     use it this way, and keep their ticket text and data out of personal
     repos.
  4. Ask: "Turn BUG-123 into test scenarios".
  5. Review the table before treating it as final. Each row should trace
     to the bug report, gaps should be open questions, and the set should
     be small (about 5 to 10 rows).
  6. Run the scenarios yourself. Every row starts as "Not run" and changes
     only after it was actually executed, on a build you name.

THE TABLE (same three columns as the other skills)
  | Test Scenarios | Test Steps | Test Result |
  Results are Pass / Fail / Blocked / Not run, each with short evidence.

TRIAL RESULT (2026-11-05)
  - 9 scenarios, all "Not run", in the required table.
  - It did NOT pick a side on a disagreement about the expected total. It
    raised it as an open question.
  - It marked unverified claims as suspected, listed what it cut, and
    said nothing shown proves the bug is fixed. It wrote no files.
  - Weak spots: one row cited a fix the run had not read, and some
    expected values were worked out by arithmetic and not confirmed.
  - After the trial the skill was tightened for both (rows on an unread
    fix must be named "Neighbour (assumed):", derived values must be
    labelled and listed as open questions).
  - RE-RUN on the same bug (2026-11-05): the unread-fix problem is fixed.
    The row was named "Neighbour (assumed):", the run said it had not
    read the fix, and traceability said so. Derived values (19.00, 45.00,
    18.00 for a single code) were labelled derived and unconfirmed and
    collected under a "Derived values" heading.
  - Bonus: it noticed 16.00 does not match "10% applied twice" (that
    would be 16.20) and asked the dev. That inconsistency came from the
    made-up ticket's own numbers, not from a planted trap.
  - One small gap remains: the derived values were not repeated in the
    open questions, as the skill asks. Still all "Not run", no side taken
    on the expected total, no files written.
  - Not exercised: reading a real fix, running the scenarios, a real
    tracker, bugs with screenshots or logs.
